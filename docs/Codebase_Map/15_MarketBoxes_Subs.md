## Read this first — the naming trap

**Two unrelated things in this codebase are called "subscription."**

| Term | What it actually is |
|---|---|
| `/api/subscriptions/*` | **Platform memberships** — vendor tiers and buyer premium. Genuine Stripe recurring subscriptions (`mode: 'subscription'`) |
| **Market boxes** | A CSA/chef-box sold as a **prepaid, fixed-term (4 or 8 week) one-time payment**. Despite the `market_box_subscriptions` table name, **there is no Stripe subscription object and no recurring charge** |

Verified: the box price is pushed as a single one-off line item into the standard checkout session with `quantity: 1`, described as *"Prepaid {n}-week subscription ({n} pickups)"* (`checkout/session/route.ts:696-705`). When the term ends, the buyer must purchase again.

Then read, in order:

1. `lib/stripe/market-box-payout.ts` (195 lines) — the entire vendor-money story, with bug history inline.
2. `api/checkout/session/route.ts:688-768` — where a box becomes a Stripe line item, and the metadata contract everything downstream depends on.
3. `api/checkout/success/route.ts:258-330` **paired with** `lib/stripe/webhooks.ts:295-370` — the dual-path idempotency design. Never read one without the other.
4. `api/market-boxes/[id]/route.ts:176-222` — the pricing/cadence rule that surprises most newcomers.

## The cadence rule

**The vendor's stated price is the buyer's pre-fee price for the term. The system never reduces it. Cadence changes the pickup *count*, not the price** (`market-boxes/[id]/route.ts:178-180`, restated at `checkout/session/route.ts:692`).

So a biweekly vendor's 4-week box delivers 2 pickups rather than 4, at the same price. Pickup cadence is a **vendor-profile-level** setting (`vendor_profiles.market_box_frequency`), not per-offering. Food trucks are **4-week only** — no 8-week option. Eight-week savings are computed against 2× the 4-week price.

The first pickup date skips manager-cancelled dates week by week, with a 60-iteration guard.

## The flow

1. **Offering creation** — the vendor POSTs to `/api/vendor/market-boxes`; `canCreateMarketBox` / `canActivateMarketBox` gate on tier. Max subscribers falls back to a tier default when unset, applied identically on both read paths.
2. **Buyer sees terms** — `/api/market-boxes/[id]` builds terms from `price_4week_cents` / `price_8week_cents` plus availability and the next start date.
3. **Purchase (primary path)** — the unified cart/checkout. The term price is validated into order pricing, the buyer fee is applied to build the line item, and the downstream contract is serialized into session metadata: `offeringId, termWeeks, startDate, priceCents (pre-fee), basePriceCents, pickupFrequency`. **`priceCents` is explicitly the pre-fee vendor-stated price**, which is what `calculateVendorPayout` consumes.
4. **Purchase (legacy direct path)** — `POST /api/buyer/market-boxes` creates a dedicated session. Note it is **stricter** than the unified path: it hard-blocks duplicate active subscriptions (`ERR_MBOX_006`), where the unified path only shows a soft warning.
5. **Subscription creation** — both the success route and the webhook call `subscribe_to_market_box_if_capacity`, an atomic capacity-checked RPC. Whichever runs first wins; the webhook is an idempotent backfill that runs on **every** delivery. Pickups are generated by a database trigger, not application code.
6. **Failure → refund** — if the RPC errors or reports at-capacity, the buyer is auto-refunded the **fee-inclusive** amount `round(priceCents × (1 + buyerFeePercent))`, matching what was actually charged. *(Refunding the pre-fee amount previously shorted buyers ~6.5%.)* A refund failure escalates to `ERR_CHECKOUT_011` / `ERR_REFUND_001` for manual intervention.
7. **Payout to vendor** — `processMarketBoxPayout`, and unlike product orders this fires **at payment time**, not fulfillment:
   - Idempotent via a non-terminal-status check mirroring a partial unique index
   - Vendor share computed off **`actualPaidCents`**, not the sticker price *(CRIT-1: previously overpaid biweekly subscriptions)*
   - A `pending` row is written **before** the transfer so failures are visible
   - `source_transaction` is threaded so the transfer queues against the specific charge rather than hitting `balance_insufficient` pre-settlement *(CRIT-2)*
   - Vendors who aren't Stripe-ready get `pending_stripe_setup` for cron retry
   - A 23505 race is a silent no-op
8. **Ongoing lifecycle** — vendors mark or skip pickups; **a skip extends the term by one week** and notifies the buyer. There is no renewal charge.

## Platform tier subscriptions

`/api/subscriptions/checkout` builds a real recurring session with `user_id / type / cycle / tier / vertical` metadata. **`vertical` is mandatory for vendors** so a webhook can't overwrite the wrong profile of a multi-vertical vendor. A tier switch cancels the existing subscription first, tolerating an already-cancelled one. `/api/subscriptions/verify` requires authentication before activating a tier.

Amounts live in `SUBSCRIPTION_AMOUNTS` (`pricing.ts:22-43`) — see [01_System_Overview.md](01_System_Overview.md) for the current table. Stripe price IDs are per-vertical env vars resolved in `lib/stripe/config.ts`.
